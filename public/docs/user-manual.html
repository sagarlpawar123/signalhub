01 · Start here

From first login to a working status page

SignalHub separates public status experiences from the authenticated organization console. Operators sign in at /login and use canonical console URLs under /organization. Visitors use a page slug, hub, feed, embed, badge, or public API.

Recommended first outcome: create one page, add one service, publish it, declare and resolve a test incident, verify delivery, and only then connect production monitors.

First Admin login

  1. Open https://your-signalhub-host/login and sign in with the bootstrap user ID and password supplied by the installation operator.
  2. Change the temporary password. If a profile field is required, complete it before continuing.
  3. Open Security, enroll MFA when required, save recovery codes offline, and verify the session list.
  4. Open Settings and confirm the organization name, slug, contact address, retention expectations, and configured identity methods.
  5. Open Pages → Create page. Choose a status page unless you are building a portfolio hub.
  6. Complete page details, add at least one visible service, review appearance, configure optional notifications, and publish.
  7. Use View public page in a private browser window. Confirm the page, history, subscription controls, and mobile layout.
  8. Create a test incident, add an update, resolve it, and verify public history and enabled destinations.

Before production use

People

  • Assign Admin, incident, responder, and viewer responsibilities.
  • Define who may publish customer communication.
  • Keep a tested local Admin recovery path.

Content

  • Name services in customer language.
  • Prepare clear incident and maintenance messages.
  • Agree on severity, impact, and update cadence.

Delivery

  • Verify SMTP and optional SMS.
  • Test Slack, Teams, and signed webhooks.
  • Confirm the worker is ready before relying on delivery.

Recovery

  • Back up PostgreSQL and assets.
  • Restore into an isolated environment.
  • Monitor SignalHub from outside its primary infrastructure.

02 · Roles and access

Give each person only the access they need

RoleUse it forCore access
AdminOrganization and installation owners/operators.All organization capabilities, users, pages, integrations, settings, and installation administration.
Incident ManagerCommunications leads and incident commanders.Incident lifecycle and updates, component updates, subscribers, and analytics.
ResponderOn-call engineers and service responders.Incident updates, monitors, component updates, and analytics.
ViewerLeadership, support, and read-only stakeholders.Analytics views.

Non-Admin memberships can be limited to selected page IDs. Page scope applies on the server and affects pages, incidents, monitors, metrics, and other page-owned resources. An empty page selection means all pages for that membership.

Menu visibility is not the security boundary. SignalHub checks authorization in server actions and API routes. If a user can see an unexpected menu item, still report it, but do not assume hidden controls are the only protection.

04 · Pages and hubs

Design the right status experience for each audience

Choose the page type

TypeUse whenAccess model
Public status pageAnyone should see health and incident history.No sign-in; optional verified subscriptions.
Private pageThe whole page is restricted to approved viewers.Access challenge and configured policy.
Audience pageDifferent users/groups should see scoped components.Audience identities and groups determine visibility.
HubA portfolio, region, brand, or business unit needs a parent directory.Contains child status pages instead of service components.

Page creation and publication

  1. Open Pages → Create page, select page or hub, choose a stable slug, and optionally assign a parent hub.
  2. Open Services & groups. For a status page, add services, use the + next to any Group field to add or manage groups, set visibility, and drag services into the order customers understand. For a hub, create or attach child pages.
  3. Open Appearance. Choose a Standard, Banner, or Compact layout, then pick a style tile (each tile previews its colors), adjust the brand color, add footer links and search details, and upload a logo, site icon, and optional cover image. Changes autosave as a draft until you select Publish changes.
  4. For private or audience pages, open Access and configure allowed identities/groups and component scope. Test with a non-Admin account.
  5. Open Notifications to review subscriber channels, set the email sender name, reply-to address, and footer, and manage team destinations and webhooks.
  6. Open Settings to set the page name, headline, about text, time zone (used for dates and maintenance windows), search-engine indexing, and destructive controls.
  7. Publish from the overview. A status page needs at least one visible service; a hub can publish its page directory.

05 · Incident operations

Communicate unplanned disruption with a durable timeline

Investigating→ Identified→ Monitoring→ Resolved

Declare an incident

  1. Confirm the affected customer experience. Do not wait for complete root-cause certainty before acknowledging a clear impact.
  2. Open Incidents → New incident, choose the page, and enter a plain-language title.
  3. Select status, severity/impact, affected services, and the first public update. State what users observe, what the team is doing, and when the next update is expected.
  4. Review whether subscriber notifications should be sent. Publish and verify the public page and delivery history.

Update cadence

  • Investigating: acknowledge symptoms and scope; avoid unsupported causes.
  • Identified: explain the known cause or failing dependency and mitigation underway.
  • Monitoring: report the mitigation and what signals are being watched.
  • Resolved: state restoration time, customer outcome, and whether a postmortem will follow.

Add a new update when state, impact, workaround, scope, or estimated recovery changes. If nothing changes, keep the promised cadence and say the investigation continues.

Edit timeline and publish a postmortem

Authorized users can correct an update while preserving the incident's durable chronology. Use edits for accuracy, not to hide operational history. After resolution, add a postmortem with impact, timeline, cause, contributing conditions, recovery, corrective actions, owners, and target dates.

Do not use maintenance for an unplanned outage. If customers are unexpectedly affected, declare an incident even when work is already underway.

06 · Maintenance

Set expectations before planned work begins

  1. Open Maintenance → Schedule maintenance, choose a page, title, start time, duration, and clear customer-facing description.
  2. Select affected services and the status they should display, normally Under Maintenance.
  3. Enable automatic transition when the worker should move the window to In Progress at the start and Completed at the end.
  4. Publish early enough for subscribers to plan. Verify timezone presentation and enabled delivery channels.
  5. At start, confirm the real work matches the announced scope. If impact becomes unexpected or exceeds the plan, open an incident.
  6. At completion, verify service health and public component state before closing the window.

07 · Monitoring and metrics

Detect failure without creating noisy public status changes

MonitorUse it forKey configuration
HTTPWeb/API availability.Method, URL, headers/body/auth, expected status range, timeout, response limit.
KeywordConfirm response content, not only reachability.Expected text and HTTP behavior.
TCPPort-level reachability.Host, port, timeout.
DNSName resolution and expected records.Name, record type, expected response.
SSL certificateCertificate validity and expiry warning.TLS hostname and threshold.
ICMPNetwork reachability where the runtime permits it.Explicit installation enablement and container/network permissions.
HeartbeatCron, backup, ETL, or job completion.Generated token URL and expected interval.

Create and tune a monitor

  1. Select the page, monitor type, target, interval, timeout, tags/group, and optional service.
  2. Set failure and recovery thresholds. Requiring consecutive outcomes prevents one transient check from flipping state.
  3. Save with automated component action disabled when possible. Use Check on next poll and inspect results, latency, and error detail.
  4. Enable component synchronization only after the monitor reliably represents customer impact.
  5. Alert operators on stale worker heartbeat, missing checks, and repeated monitor errors.
Private targets are denied by default. Enabling private-target monitoring expands network reach. Place workers in a controlled monitoring network and restrict egress before enabling it.

Metrics

Metrics are numeric time series displayed on a status page. Create a name, optional unit suffix, and optional component link. Push points manually for validation or through POST /api/v1/manage/metrics/<id>/points. A chart appears publicly after it has data. Metrics explain performance; monitors determine check state.

08 · Subscribers and delivery

Send the right update through verified channels

ChannelAudienceReadiness requirement
EmailVerified page subscribers.SMTP configured and delivery worker healthy.
SMSVerified phone subscribers where enabled.Twilio settings, enabled platform policy, healthy worker.
Slack / TeamsInternal or customer team channels.Destination enabled and tested before save.
Signed webhookAutomation and downstream incident systems.Verified HTTPS endpoint, saved secret, signature validation, idempotent receiver.
RSS / AtomFeed readers and polling integrations.Public feed or revocable signed token for protected access.

Subscriber workflow

Visitors request a one-time code and verify ownership before activation. Administrators use Subscribers to filter by page/channel, import approved email contacts, quarantine a contact without deleting it, and export CSV. Treat subscriber contact information as protected operational data.

Delivery troubleshooting order

  1. Confirm the worker is ready and recently heartbeating.
  2. Confirm the provider is enabled in installation configuration.
  3. Confirm tenant credentials and destination verification state.
  4. Inspect the queued attempt, retry schedule, last error, and dead-letter state.
  5. Send a controlled test before replaying a broad set of deliveries.

09 · Integrations and APIs

Automate with scoped credentials, not browser sessions

Management API keys

  1. Open API Keys, select the page context, name the integration, and choose only required scopes.
  2. Add page restrictions, expiration, and source CIDRs where practical.
  3. Copy the token once into a secret manager. SignalHub stores its hash and cannot show the full token again.
  4. Send Authorization: Bearer <token> to /api/v1/manage/*.
  5. Rotate before expiry or immediately after suspected exposure; revoke the old key and verify audit evidence.
curl -fsS https://status.example.com/api/v1/manage/incidents \
  -H 'Authorization: Bearer <api-key>' \
  -H 'Content-Type: application/json' \
  --data '{"pageId":"<page-id>","title":"Elevated API errors","status":"INVESTIGATING"}'

Use the live OpenAPI 3.1 contract at /api/openapi as the authoritative request/response reference for the deployed version.

Purpose-specific integrations

  • Component automation token: updates one component through /api/v1/webhook-component/:token.
  • Heartbeat token: records expected job activity through /api/v1/heartbeat/:token.
  • Embed: incident banner script for another site.
  • Badge: compact dynamic status response.
  • Public status API: page health JSON with page access rules enforced.
  • Feeds: RSS/Atom for public pages or revocable signed access.

Signed outbound webhooks

Register and test an HTTPS endpoint, copy its secret once, and validate the HMAC signature against the exact raw request body. Reject invalid timestamps/signatures, process event IDs idempotently, return success promptly, and move slow work to the receiver's queue. Rotate secrets after exposure.

10 · Users and security

Manage human identity and session risk

Create an organization user

  1. Open Users & Roles and enter name, user ID, email, role, and optional page scope.
  2. For a new local identity, set a temporary password through the protected workflow. The user must change it at first sign-in.
  3. For an existing identity, add the organization membership without replacing its current authentication method.
  4. Review access after role changes, team transfers, and incident rotations. Remove or revoke access immediately when no longer needed.

Security menu

  • Enroll TOTP MFA and store recovery codes offline.
  • Review active sessions and revoke unknown or stale sessions.
  • Change passwords through the authenticated flow; relevant sessions are revoked.
  • Configure OIDC or SAML using the callback/metadata values shown by SignalHub.
  • Test identity connections before enforcing them.
  • Create and rotate SCIM bearer tokens; test create, update, group mapping, disable, and delete behavior.
Preserve recovery access. Before enforcing SSO or changing role mappings, verify a local Admin account, MFA recovery material, canonical URL, and direct database-backed sign-in path.

12 · Public visitor guide

How customers and employees use a status page

  • The page header communicates overall status. Service groups explain which capabilities are affected.
  • By default, the status page lists active incidents and active maintenance. Completed maintenance and resolved incidents remain available on the separate History page; upcoming maintenance is not shown in these sections.
  • History contains resolved incidents, completed maintenance, and available postmortems.
  • Metrics show published numeric history such as response time or uptime.
  • Visitors subscribe by requesting and entering a one-time verification code, for all services or only chosen ones, and email subscribers receive a confirmation. Every message links to a preferences page where they can change services or unsubscribe; mail clients also offer one-click unsubscribe.
  • RSS and Atom support feed readers. Protected pages may require a revocable signed feed URL.
  • Private and audience pages show an access challenge and only reveal content allowed by policy.

Operators should test visitor workflows without an Admin session and with assistive/mobile layouts before launch.

13 · Operating runbooks

Repeatable checks for a dependable status service

Each operator shift

  • Review dashboard, active incidents, upcoming maintenance, worker readiness, queue depth, and dead letters.
  • Confirm external monitoring can reach public pages.
  • Handoff open communication commitments and next-update times.

Weekly

  • Review failed monitors, noisy thresholds, delivery retries, certificate warnings, stale API keys, and audit anomalies.
  • Confirm backups completed and asset protection is healthy.
  • Review scheduled maintenance and its customer-facing communications for accuracy.

Monthly

  • Review users, roles, page scopes, sessions, API keys, webhook endpoints, and identity mappings.
  • Patch the base image and dependencies through the organization's release process.
  • Verify audit chains and SIEM delivery.

Quarterly

  • Restore PostgreSQL and assets into an isolated environment.
  • Test Admin recovery, MFA recovery codes, SSO failover, and SCIM deprovisioning.
  • Exercise a test incident, maintenance window, subscriber delivery, webhook verification, and key rotation plan.

Safe upgrade sequence

  1. Review release notes, environment template, chart values, migrations, and dependency findings.
  2. Create and verify a database and asset backup.
  3. Build/pull the reviewed immutable image; run preflight and migration check.
  4. Run the migration once, then roll workers and web replicas according to the deployment guide.
  5. Validate readiness, migration state, login, public pages, monitors, queues, and delivery.

15 · Glossary

SignalHub terms

Organization
A tenant boundary containing memberships, pages, incidents, monitors, subscribers, integrations, and audit data.
Status page
A visitor-facing service-health experience identified by its slug.
Hub
A parent directory of status pages for a portfolio, business unit, region, or brand.
Service / component
A customer-understandable capability whose effective health may come from manual state, incidents, maintenance, and monitors.
Incident
An unplanned service-impact record with status, severity/impact, affected services, updates, resolution, and optional postmortem.
Maintenance
A planned service window with scheduled lifecycle and affected services.
Monitor
A worker-executed availability check with failure and recovery thresholds.
Metric
A numeric time series published as a chart.
Subscriber
A verified contact that follows a status page through an enabled channel.
Destination
A tested team channel or signed webhook endpoint receiving status events.
Worker
The background runtime for checks, notifications, exports, audit delivery, retention, maintenance transitions, and lifecycle jobs.
Installation administration
Admin-only cross-organization controls under /organization/platform.
